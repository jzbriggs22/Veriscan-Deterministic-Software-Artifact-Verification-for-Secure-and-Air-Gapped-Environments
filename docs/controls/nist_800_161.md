## Introduction to Supply Chain Risk Management (SCRM)

NIST Special Publication 800-161 Revision 1, *Cybersecurity Supply Chain Risk Management Practices for Systems and Organizations* (May 2022), provides guidance for organizations to identify, assess, and respond to cybersecurity risks throughout the supply chain. It extends NIST SP 800-53 Rev 5's SA-12 (Supply Chain Protection) control family with a comprehensive set of C-SCRM practices.

SP 800-161 Rev 1 organizes C-SCRM at three operational levels:

- **Level 1 — Organization:** Governance, policy, and risk management strategy.
- **Level 2 — Mission/Business Process:** Supplier relationships, acquisition processes, risk acceptance criteria.
- **Level 3 — System/Operational:** Technical controls at system integration points, artifact verification, component authentication.

Veriscan operates primarily at **Level 3** — the technical implementation layer — providing cryptographic artifact verification controls at the software artifact intake point. However, its declarative policy engine, policy digest binding, and structured evidence model also contribute to Level 2 governance and auditability.

## Disclaimer

This mapping is informational and does not constitute a formal assessment, audit finding, or certification claim. Organizations implementing NIST SP 800-161 Rev 1 must conduct their own C-SCRM assessments. The mappings below identify where Veriscan's technical features support the intent of the referenced practices; they do not substitute for a complete organizational C-SCRM program.

## C-SCRM Key Practices from SP 800-161 Rev 1

In addition to the SR control family, SP 800-161 Rev 1 identifies key practices (KP) for C-SCRM implementation. The following practices are relevant to Veriscan deployments.

| Key Practice | Description | Veriscan Contribution |
|---|---|---|
| KP-3.2 | Identify and prioritize critical components based on risk | Static inspection flags executable types (ELF, PE, Mach-O, scripts) and high-entropy artifacts. Policy's `deny_file_types` and `executable_handling` apply stricter controls to high-risk component types. |
| KP-3.3 | Use approved suppliers only | The `allow_signers` list in policy enforces that artifacts must be signed by pre-approved supplier keys. Artifacts signed by unknown keys receive `SignerNotAllowed` verdict (FAILED under `contractor_strict` or `airgapped` policies). |
| KP-3.4 | Establish requirements for suppliers | The YAML policy file serves as a machine-enforceable artifact acceptance specification. Organizations can require suppliers to provide checksums, PGP signatures, and (Phase II) SBOMs as part of delivery packages. |
| KP-3.5 | Obtain and preserve provenance data for all acquired products | Veriscan captures and records: source URL or local path, file size, SHA-256 at acquisition, SHA-512 at acquisition, PGP signer fingerprint and user ID, ClamAV engine version and result, VirusTotal engines total and detected count, file type, and Shannon entropy. All data is preserved in the JSON report with tamper-evident evidence records. |
| KP-3.6 | Employ continuous monitoring | CI/CD pipeline integration via deterministic exit codes enables continuous re-verification of artifacts as the threat landscape evolves. VirusTotal reputation cache TTL (`reputation_cache_ttl_seconds`) controls re-query frequency, enabling periodic re-checks against updated threat intelligence databases. |

## Air-Gapped Environment SCRM Controls

NIST SP 800-161 Rev 1 provides specific guidance for high-security isolated environments. Veriscan's offline bundle format is designed to satisfy C-SCRM requirements in these contexts.

### Offline Bundle Workflow

The offline bundle workflow satisfies C-SCRM artifact provenance requirements for air-gapped environments:

**Step 1: Bundle Creation (in the connected environment)**
```bash
veriscan bundle create \
    --artifact artifact.tar.gz \
    --keys /path/to/keys/ \
    --signing-key /path/to/secret.asc \
    --out /media/transfer/artifact_bundle/
```

The bundle includes: artifact, SHA-256/SHA-512 checksums, PGP signature, trusted public keys, and a PGP-signed manifest covering all bundle files.

**Step 2: Transfer**
The bundle is transferred to the air-gapped environment via approved removable media (consistent with organizational media transfer policies).

**Step 3: Verification (in the air-gapped environment)**
```bash
veriscan verify \
    --policy policies/airgapped.yaml \
    --offline /media/transfer/artifact_bundle/
```

Verification order (fail-closed):
1. Load trusted keys from `bundle/trusted_keys/`.
2. Verify `bundle.manifest.sig` over `bundle.manifest.json` — no other bundle file is trusted until this passes.
3. Verify SHA-256 of every file listed in the manifest.
4. Run the full pipeline (hash, signature, malware, inspect) on the verified artifact.

### Air-Gapped Policy Configuration

The included `airgapped.yaml` policy enforces appropriate controls for disconnected environments:

```yaml
allow_network: false          # No outbound connections; network attempts rejected
require_signature: true       # PGP signature is the offline trust anchor
require_checksums: true       # Checksums required
malware_scan_required: true   # ClamAV must be present locally
malware_failure_is_fatal: true # Missing scanner is fatal in controlled offline env
reputation_required: false    # VT unavailable offline; not required
executable_handling: block_unsigned  # Unsigned executables blocked
```
