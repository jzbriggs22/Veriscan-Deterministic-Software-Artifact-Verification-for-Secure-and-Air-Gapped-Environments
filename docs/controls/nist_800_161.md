# NIST SP 800-161 Rev 1 Control Mapping

**NIST SP 800-161 Rev 1** — *Cybersecurity Supply Chain Risk Management Practices for Systems and Organizations*

This document maps `veriscan` capabilities to relevant C-SCRM practices and controls.

---

## Overview

NIST SP 800-161 Rev 1 establishes cybersecurity supply chain risk management (C-SCRM) practices at three levels:
- **Level 1**: Organization-wide governance
- **Level 2**: Mission/business process
- **Level 3**: System/operational implementation

`veriscan` primarily addresses **Level 3** operational controls — the technical implementation of artifact integrity verification at system ingestion points.

---

## Relevant Practice Areas

### SR — Supply Chain Risk Management (from NIST SP 800-53 Rev 5)

#### SR-3: Supply Chain Controls and Processes
**Practice**: Establish a process or processes to identify and address weaknesses or deficiencies in the supply chain elements and processes.

**veriscan implementation**:
- Mandatory verification pipeline cannot be bypassed or shortcut
- Policy YAML defines organization-specific acceptance criteria
- FAILED verdict blocks artifact promotion with evidence of why
- Decision trace documents exactly which rule produced the verdict

#### SR-4: Provenance
**Practice**: Document, monitor, and maintain valid provenance of the following systems, system components, and associated data.

**veriscan implementation**:
- Hash stage computes SHA-256/SHA-512 and optionally verifies against expected checksums, establishing cryptographic identity
- Signature stage verifies PGP provenance: signer UID, fingerprint, and key material
- Evidence chain records source URL/path, acquisition timestamp, and hash-at-acquire
- Offline bundle format includes provenance artifacts (checksums, signatures, trusted keys) co-located with artifact

#### SR-5: Acquisition Strategies, Tools, and Methods
**Practice**: Employ the following acquisition strategies, contract tools, and procurement methods to protect against, identify, and mitigate supply chain risks.

**veriscan implementation**:
- Standardized verification tooling provides consistent intake process
- Policy as code ensures audit-reproducible verification decisions
- Machine-readable JSON output enables integration into acquisition tracking systems
- Exit codes (0/10/20/99) map to actionable CI/CD pipeline decisions

#### SR-6: Supplier Assessments and Reviews
**veriscan implementation**:
- Signer allowlists (`allow_signers`) enforce that only pre-approved supplier signing keys are accepted
- VirusTotal reputation lookup provides independent third-party threat intelligence
- ClamAV malware scanning provides local-enforcement malware screening at intake

#### SR-10: Inspection of Systems or Components
**Practice**: Inspect the following systems or system components.

**veriscan implementation**:
- Static inspection stage examines file type, entropy, and behavioral indicators without execution
- Inspection results included in evidence for auditor review
- High-entropy artifacts (potentially packed/encrypted) are flagged per policy threshold
- URL, PowerShell, and base64 indicators extracted for analyst review

#### SR-11: Component Authenticity
**Practice**: Employ the following controls to verify the integrity and authenticity of the following systems or components.

**veriscan implementation**:
- SHA-256 and SHA-512 verification proves bit-for-bit integrity
- PGP detached signature verification with key pinning proves authenticity
- Both hash and signature evidence included in machine-readable audit report
- For offline environments: bundle manifest signature provides root of trust for all bundle contents

#### SR-11(1): Anti-Counterfeit Training
**veriscan implementation**: Policy validation commands and the `policy-validate` subcommand provide analyst training artifacts demonstrating correct vs incorrect verification configurations.

#### SR-11(2): Configuration Control for Component Service / Repair
**veriscan implementation**: All verification parameters (policy, expected hashes, trusted keys) are explicit, versioned, and logged in evidence. No implicit or default-accepting behaviors.

## C-SCRM Key Practices from SP 800-161 Rev 1

### KP-3.2: Identify and Prioritize Critical Components
**veriscan contribution**: Artifact inspection (file type, executable status, entropy) provides measurable indicators for criticality assessment. Organizations can configure `deny_file_types` and `executable_handling` in policy to apply stricter controls to high-risk component types.

### KP-3.3: Use of Approved Suppliers
**veriscan contribution**: Signer key pinning (`allow_signers` in policy) enforces that artifacts must be signed by pre-approved supplier keys. Any artifact signed by an unknown key receives `SignerNotAllowed` result (FAILED under strict policies).

### KP-3.4: Requirements for Suppliers
**veriscan contribution**: Policy YAML serves as a machine-enforceable artifact acceptance specification. Organizations can require suppliers to provide specific artifacts (checksums, signatures, SBOM) as part of the acceptance bundle.

### KP-3.5: Obtain Provenance Data for All Acquired Products
**veriscan contribution**: Acquires and records provenance data: source URL, SHA-256/SHA-512, PGP signature, signer identity, and ClamAV scan result. All data captured in structured evidence with deterministic IDs.

### KP-3.6: Employ Continuous Monitoring
**veriscan contribution**: CI/CD integration (exit codes + JSON output) enables continuous re-verification of artifacts as threat intelligence evolves. VirusTotal reputation cache TTL controls re-query frequency.

## Air-Gapped Environment Specifics

NIST SP 800-161 includes specific guidance for organizations with high-security or isolated environments.

### Offline Bundle Support
`veriscan` provides a cryptographically-secured offline bundle format that enables air-gapped deployment:

1. **Bundle creation** (online): Artifact is hashed, signed, and packaged with trusted keys and a signed manifest
2. **Transfer**: Bundle is moved to the air-gapped environment via approved media
3. **Bundle verification** (offline): Manifest signature verified first; all file hashes checked; then full pipeline runs on the artifact

This workflow satisfies C-SCRM requirements for artifact provenance in environments where network connectivity is not permitted.

### Policy Controls for Air-Gapped Environments

The included `airgapped.yaml` policy enforces:
```yaml
allow_network: false          # No outbound connections permitted
require_signature: true       # Signature required (offline trust anchor)
malware_scan_required: true   # ClamAV must be available locally
malware_failure_is_fatal: true
reputation_required: false    # VT unavailable; not fatal
```
